# 地図ヒント強化PoC（東京・上野・京都）

検証日：2026-10-15。対象ブランチ：`feature/map-hints-poc`。

東京・上野・京都だけに施設アイコン、初期500mの新幹線種別表示、確認済み路線カラーを追加した。駅カタログは50駅のまま、Easy 34駅 / Hard 50駅、4択、10問、採点、ヒント、再プレイ、画面遷移は変更していない。残り47駅は従来の補助データと表示タイミングを使う。

## 実装

- `map_hints_poc.json`をデータ正本とし、対象駅IDを`tokyo`、`ueno`、`kyoto`に限定した。対象外駅ではこのアセットを読み込まず、従来のスタイルを生成する。
- 学校・大学、病院、神社・寺院、博物館・美術館、大型商業施設、スタジアムの6分類を共通処理する。48pxのMaterial Iconsベクターグリフから端末内で淡色PNGを1回生成する。iOSでは3x端末上の固有サイズが16ptとなり、従来の0.5倍表示は実質約8ptで小さすぎた。2026-10-15に、初期500mの約24ptからヒント2の約18ptまで滑らかに縮小するズーム連動サイズへ変更した。外部画像や絵文字は使わない。
- 実行用施設featureは`kind`、`rank`、`osm_type`、`osm_id`だけを持つ。施設名、駅名、タップ処理、ポップアップ情報は含まない。地図全体も既存どおり操作を遮断する。
- 選定施設は1駅5件以下。匿名の分類アイコンは初期〜ヒント2で表示し、後から現れる路線名との衝突で消えない設定にした。文字レイヤーの配置を妨げない。
- ヒント3の約5km表示では匿名アイコンを隠し、名称付きの代表施設だけを駅ごとに3件選んで表示候補にする。施設名が衝突で省略された後に点だけ残っていたため、東京・上野・京都では従来の施設円マーカーも表示しない。残り47駅の従来表示は変更しない。
- 初期500mから、新幹線の実線形だけを白縁の低彩度紫線で重ね、通常の線路表示と区別する。初期画面に凡例を表示するが、路線名・事業者名・ブランド色は出さない。この種別表示はヒント後も維持する。
- 路線は確認済みOSM route relationに属する実wayだけを使う。全頂点を保持し、端点が完全一致するwayだけを連結する。近接だけを理由に線路を接続しない。
- 路線カラーは初期では非表示、ヒント1から表示する。既存の650msズームを維持し、ヒント2で路線名、ヒント3で既存の地名・代表施設名を追加する。
- アイコン生成失敗時は失敗したFutureを破棄して再試行可能にした。ヒント切替中にnative idleが来た場合も描画確認を再実行し、条件が揃っているのに25秒でタイムアウトする競合を防いだ。タイムアウト値自体は変更していない。

| 段階 | 範囲 | 東京・上野・京都 | 得点 |
|---|---:|---|---:|
| 初期 | 約500m | 従来の線路・建物・道路＋施設アイコン＋新幹線種別表示 | 100 |
| ヒント1 | 約1km | 上記＋確認済み路線カラー | 70 |

## 施設データ

選定した14件は、OpenFreeMapの2026-10-11タイルスナップショットの`poi` featureに実在することを確認し、そのタイル座標を緯度経度へ変換した。同じOSM IDの2026-10-14 Overpass応答とも照合した。タイル位置とOSMノードまたはエリア中心の差は全件150m未満、駅中心からは全件500m未満である。実行用アセットに名称はコピーしていない。

初期の「約500m」は地図短辺全体の幅なので、駅から約250mより外側の選定施設はヒント1で画面内に入る。データ件数と初期描画件数を分けて記録する。

| 駅 | 選定データ | 初期に描画 | 初期の種類 | ヒント1以降に加わる種類 |
|---|---:|---:|---|---|
| 東京 | 4 | 3 | 文化1、商業2 | 教育1 |
| 上野 | 5 | 3 | 文化2、教育1 | 文化1、宗教1 |
| 京都 | 5 | 2 | 商業2 | 文化1、教育1、宗教1 |

病院とスタジアムは共通アイコンを実装したが、今回の3駅で選定条件を満たす候補を採用していない。件数を埋めるための施設や座標は生成していない。

ヒント3では既存の検証済み名称データから次の代表施設だけを候補にする。文字同士が重なる場合はMapLibreが配置を省略するため、実画面に出る名称はこの候補の部分集合になる。

| 駅 | ヒント3の代表施設候補 |
|---|---|
| 東京 | 東京国立近代美術館、インターメディアテク、国立映画アーカイブ |
| 上野 | 国立西洋美術館、国立科学博物館、東京国立博物館 |
| 京都 | 京都タワー、京都国立博物館、京都鉄道博物館 |

取得証跡は[sources.json](sources.json)に、クエリ、OSM base timestamp、タイルURL・z/x/y・extent、元OSM要素、タイルfeature、使用relation/way、入力ファイルのSHA-256を保存した。実行用アセットは`assets/maps/map_hints_poc.json`、再生成処理は`tool/prepare_map_hints_poc.py`である。

## 路線カラー

### 初期500mの新幹線種別表示

OpenFreeMapの`transportation`タイルでは新幹線と在来線がともに`class=rail` / `subclass=rail`となり、`highspeed`、路線名、軌間などの判別属性は配信されていない。地下・高架・線形だけから推測すると誤分類するため、タイル属性による自動判定は採用しなかった。

代わりに、既存の`station_hints.json`へ保存済みの実OSM railway geometryから、駅別に承認した名称かつ駅中心500m以内を通るfeatureだけを選んだ。東京は東海道・東北新幹線、上野は東北新幹線、京都は東海道新幹線が対象である。上野用の8km取得データに含まれる東京駅付近の東海道新幹線は約3.47km離れているため除外する。MapLibreへ渡す専用GeoJSONでは元の名称を削除し、`railType: highSpeed`だけを保持する。これにより、線種は判別できるが正解駅名や新幹線名は初期画面へ漏れない。

[high-speed-rail-audit.json](high-speed-rail-audit.json)には、駅別の根拠way ID、supporting relation ID、駅までの最短距離、取得raw/queryのSHA-256、OSM base timestampを保存した。[high-speed-rail-osm-evidence.json](high-speed-rail-osm-evidence.json)には、3つの保存rawから対象22 wayのタグ・geometryと4 relationのタグ・該当memberをそのまま抜粋した。駅近傍の根拠wayはすべて`railway=rail`、`highspeed=yes`、`usage=main`、`gauge=1435`で、`service`なしである。テストでは実タグ、relation membership、raw geometryの全辺が対象LineStringに含まれること、駅中心500m以内であること、raw/queryのhashが[sources.json](sources.json)と一致することを検査する。

白縁の低彩度紫は線種を示すPoC固有色であり、事業者・列車・路線のブランド色を表さない。通常の線路は既存表示のまま残し、その上に検証済みの新幹線形状だけを重ねた。東京・上野・京都以外の47駅には専用source、layer、凡例を追加していない。

### ヒント1以降の確認済み路線カラー

OpenFreeMapの検証用z14タイルでは、`transportation`の線形と`rail` / `subway`分類は取得できたが、各線形を旅客サービスへ一意に結ぶroute relation IDや路線カラーは得られなかった。`transportation_name`にも検証した中心タイルでは対象となる鉄道路線名featureがなかった。このため、位置だけで路線を推測せず、Overpassで取得したOSMの`type=route`かつ`route=train|subway` relationと構成wayを使用した。

RGBは記載したOSM relationの`colour`タグをそのまま使い、事業者一次資料で路線同定と色相を確認した。事業者のブランド仕様RGBと同一であるとは断定しない。

今回色分けしなかった主な路線は次のとおり。技術的に架空色を付ける代替は行わず、未確認の線路は従来色のまま残した。

| 駅 | 今回色分けしなかった主な路線・列車 | 理由 |
|---|---|---|

同じOSM wayが複数の採用サービスに属する場合は、2.8px間隔の細線を左右へ並べる生成処理を用意した。今回採用したwayには共有区間がなく、全`lineOffset`は0である。共有線路の実描画は未検証で、50駅展開前の追加PoCが必要。

2026-10-15にiPhone「いほん」（iPhone 16 / iOS 26.6.2）で確認した。初期500mの新幹線種別表示、アイコン拡大、ヒント3の代表施設表示を含むコミット`565490d`からrelease版`Runner.app`を署名ビルドし、`devicectl`でインストールした。bundle ID `jp.ekidoko.ekidoko`、アプリ版1.0.0（build 1）が端末のインストール済みアプリ一覧に登録され、起動コマンドが成功した後もRunnerプロセスが端末上で稼働していることを確認した。

端末を人が操作する必要がある通常10問のプレイ、施設アイコンの有用性、路線カラーがヒントとして強すぎないかの評価は未確認。インストールと起動成功を、ゲーム性の手動確認済みとは扱わない。

## 50駅展開前の作業

1. 各駅で代表施設と全候補路線を人が確認し、OSM relation・公式資料・名称漏洩をレビューする。固定IDの手作業が現在の主なボトルネック。
2. 今回の施設候補確認は駅中心を含む単一z14タイルを使った。東京と上野は500m表示域が隣接タイルへまたがるため、候補網羅には周囲タイル取得またはOverpass位置を正本にする処理が必要。
3. 共用線路を持つ実例で、複数色のオフセット、地下・地上の重なり、色覚多様性、路線数が多い駅の密度を実機確認する。
4. 路線relation、施設、タイルは更新される。新幹線の現行判定は駅別の承認名称と500m距離に依存するため、未命名線や名称変更を自動追従しない。生成時の欠落を失敗にする現在の検査を維持し、`highspeed=yes`を含む取得日・入力hash・差分レビューを残す。
5. 3駅の実行アセットは約100KB、監査証跡は約1MB。単純比例では50駅で実行データ約1.7MB、証跡約17MBに達する。駅別遅延読込、共通service geometryの重複排除、監査データの配布分離を検討する。
6. iPhoneで通常の10問をプレイし、初期〜H2の約18〜24ptアイコン、初期500mの新幹線区別、H3の代表施設名、路線色の強さを評価する。必要なら件数・サイズ・新幹線とH1の線幅を調整してから対象駅を増やす。
